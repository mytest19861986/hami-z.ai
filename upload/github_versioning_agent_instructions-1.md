# دستور اجرایی مدیریت خودکار نسخه‌ها و تحویل پروژه از طریق GitHub

## هدف
پروژه اکنون حدود ۶۰٪ پیشرفت دارد و تاکنون ممکن است نسخه‌بندی منظم نداشته باشد. از این لحظه، مدیریت Git/GitHub را **مستقل و خودکار** انجام بده تا:

1. وضعیت فعلی و تمام پیشرفت‌های بعدی در GitHub قابل بازیابی باشند.
2. هر مرحله مهم، نقطه بازگشت مشخص (Checkpoint) داشته باشد.
3. عامل برنامه‌نویسی دیگری بتواند با دریافت مخزن و انتخاب یک نسخه مشخص، پروژه را روی سرور راه‌اندازی کند.
4. برای کارهای معمولِ Commit، Push، ساخت شاخه و Checkpoint مرتباً از من تأیید نخواهی.

## ۱. بررسی و حفاظت از وضعیت موجود؛ پیش از هر تغییر

- وضعیت فایل‌ها، شاخه‌ها، `git status`، تاریخچه Commitها، Remoteها و دسترسی مخزن GitHub را بررسی کن.
- فایل‌های تغییرنیافته، تغییرات ثبت‌نشده و فایل‌های خارج از Git را شناسایی کن؛ **هیچ‌چیز را پاک نکن**.
- اگر Git فعال نیست، آن را با حفظ فایل‌های موجود راه‌اندازی کن. اگر مخزن قبلاً تاریخچه دارد، همان تاریخچه را حفظ کن؛ مخزن را بی‌دلیل از نو نساز.
- فایل‌های حساس، توکن‌ها، رمزها، کلیدهای خصوصی، دیتابیس‌های واقعی و `.env` را پیش از هر Commit یا Push شناسایی و از انتشارشان جلوگیری کن. `.gitignore` و `.env.example` امن را تنظیم کن.
- وضعیت فعلیِ قابل‌ثبت را در شاخه‌ای امن ثبت کن و آن را به GitHub بفرست؛ این نقطه را با عنوان روشن، مانند `baseline-current-60-percent`، مستند کن. نام واقعی را با وضعیت مخزن هماهنگ کن.
- وجود موفق Checkpoint روی GitHub را با شناسه Commit و نتیجه Push تأیید کن. اگر Push ناموفق بود، ادعای ذخیره شدن در GitHub نکن.

## ۲. بازیابی «نقطه‌به‌نقطه» پیشرفت گذشته

- تاریخچه Git، نسخه‌های محلی، نسخه‌های پشتیبان، فایل‌های آرشیوی و دیگر آثار واقعیِ موجود را بررسی کن.
- اگر مراحل قدیمی واقعاً قابل بازیابی‌اند، آن‌ها را **به ترتیب و بدون تحریف تاریخچه موجود** به نقاط مشخص قابل شناسایی تبدیل کن و برای هر کدام توضیح بنویس.
- **از روی کد فعلی نسخه‌های قدیمی خیالی نساز.** اگر سابقه کافی وجود ندارد، صریح بنویس: «بازسازی واقعی مراحل گذشته ممکن نیست؛ نخستین نقطه قابل اتکا وضعیت فعلی پروژه است.»
- اگر تاریخچه‌ای بازسازی شد، منشأ و میزان اطمینان هر نقطه را مشخص کن؛ تاریخ و ترتیب ساختگی به آن نده.
- یک جدول کوتاه از نقاط واقعی قابل بازیابی تهیه کن: نام مرحله، شرح تغییرات، شاخه، Commit SHA، Tag (اگر دارد)، وضعیت Push.

## ۳. نسخه‌بندی خودکار از این لحظه

خودت براساس نوع و اهمیت تغییر، زمان مناسب ثبت نسخه را تشخیص بده:

- **Commit:** بعد از هر واحد تغییر معنادار و قابل توضیح؛ نه برای هر خط کد و نه فقط در پایان پروژه.
- **Checkpoint:** پیش از تغییرات بزرگ یا پرریسک، پس از پایان هر قابلیت مهم و هنگام توقف کار با تغییرات معنادار.
- **Tag یا Release:** پس از رسیدن به یک نقطه نسبتاً پایدار و تست‌شده که باید به‌صورت مشخص قابل بازیابی یا تحویل به عامل استقرار باشد.
- هر ثبت را پس از بررسی و تست مرتبط، به شاخه مجاز در GitHub **Push** کن. شکست تست یا Push را گزارش و پیگیری کن؛ نتیجه ناموفق را «نسخه سالم» ننام.
- برای Commitها از `feat:`, `fix:`, `refactor:`, `test:`, `docs:` و پیام‌های توصیفی استفاده کن.
- برای نسخه‌های آماده تحویل از شماره‌گذاری روشن مانند `v0.1.0`, `v0.2.0`, `v1.0.0` و برای نقاط کاری از نام‌های واضح استفاده کن. هر Tag باید به Commit دقیق و مشخص اشاره کند؛ Tagهای منتشرشده را جابه‌جا نکن.
- شاخه‌های کنونی مخزن را ابتدا بررسی کن؛ برای قابلیت‌های جدید در صورت نیاز `feature/*` و برای رفع اشکال `fix/*` بساز. ساختار `main`/`develop` را فقط اگر با وضعیت پروژه سازگار است پیاده کن؛ شاخه‌های موجود را تخریب نکن.
- ادغام در شاخه پایدار فقط پس از عبور از تست‌ها و کنترل‌های تعریف‌شده پروژه انجام شود. الزامات امنیتی و محافظت شاخه‌ها را دور نزن.

## ۴. آماده‌سازی برای تحویل به عامل دوم و نصب روی سرور

GitHub باید **منبع اصلی کد قابل تحویل** باشد. برای اینکه عامل دیگری بتواند نسخه انتخابی را راه‌اندازی کند، این موارد را مطابق فناوری واقعی پروژه تهیه یا تکمیل کن:

- `README.md`: معرفی پروژه، پیش‌نیازها و راه‌اندازی محلی.
- `CHANGELOG.md`: تغییرات مهم هر نسخه و Checkpoint.
- `docs/DEPLOYMENT.md`: پیش‌نیازهای سرور، وابستگی‌ها، دستورهای نصب، Build، اجرا، تست سلامت، لاگ‌ها و روش بازگشت به نسخه قبلی.
- `.env.example`: نام متغیرهای محیطی لازم **بدون هیچ مقدار محرمانه**؛ روش امن تأمین Secrets را توضیح بده.
- فایل‌های قفل وابستگی‌ها، تنظیمات ساخت، مهاجرت‌های دیتابیس و فایل‌های پیکربندی لازم برای راه‌اندازیِ قابل تکرار را در مخزن نگه دار.
- اگر پروژه از Docker/Compose یا CI استفاده می‌کند، فایل‌ها و دستورهای مربوط را به‌روز نگه دار؛ ابزار تازه را فقط در صورت نیاز واقعی اضافه کن.
- در پایان هر نسخه قابل تحویل، **شناسه دقیق Commit یا Tag**، شاخه، وضعیت تست، پیش‌نیازهای استقرار و تغییرات دیتابیس را در گزارش بنویس تا عامل دوم دقیقاً همان نسخه را دریافت کند.
- **صرفِ بازگرداندن Commit به معنی بازگرداندن داده‌های دیتابیس نیست.** برای مهاجرت، پشتیبان‌گیری و بازیابی داده‌ها راهنمای مستقل ارائه کن.

## ۵. میزان استقلال و موارد استثنایی نیازمند تأیید

برای این کارهای معمول **به من پیام تأیید نده**: بررسی وضعیت Git، ثبت Commit، Push به شاخه کاری مجاز، ساخت شاخه، ساخت Checkpoint و Tag جدید، به‌روزرسانی مستندات، اجرای تست و گزارش‌دهی. این کارها را بخشی از روال دائمی توسعه بدان.

اما بدون مجوز صریح، کارهای **مخرب یا دارای اثر بیرونی** انجام نده: `force push`، بازنویسی یا حذف تاریخچه، حذف شاخه‌های اصلی، پاک‌کردن فایل‌های مهم، انتشار اطلاعات حساس، حذف/ریست دیتابیس واقعی یا استقرار روی سرور عملیاتی. اگر چنین کاری ضروری شد، فقط همان مورد استثنایی را با دلیل و گزینه امن‌تر مطرح کن؛ کارهای مستقل دیگر را ادامه بده.

## ۶. خروجی مورد انتظار و شروع فوری

**همین حالا و بدون پرسیدن تأییدهای تکراری:**

1. مخزن و وضعیت واقعی پروژه را بررسی کن.
2. در صورت وجود شواهد معتبر، نقاط تاریخی گذشته را استخراج کن؛ موارد غیرقابل بازیابی را صادقانه مشخص کن.
3. از وضعیت فعلی یک نقطه بازگشت امن و قابل بازیابی در GitHub بساز.
4. روال خودکار Commit/Push/Checkpoint/Tag را برای ادامه توسعه برقرار کن.
5. مدارک لازم برای تحویل نسخه مشخص به عامل استقرار را آماده کن.
6. توسعه عادی پروژه را ادامه بده و بعد از هر مرحله مهم فقط **گزارش نتیجه** بده، نه درخواست تأیید.
